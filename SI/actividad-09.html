Red team report: pentesting de My File Server 1

Evaluación ofensiva controlada de un servidor de archivos vulnerable, desarrollada con metodología PTES/OWASP, desde reconocimiento hasta escalada de privilegios a root mediante la vulnerabilidad DirtyCow.

Introducción

Esta actividad documenta un ejercicio de pentesting realizado sobre la máquina vulnerable My File Server 1 en un entorno de laboratorio aislado. El objetivo fue evaluar la postura de seguridad del servidor mediante una simulación de ataque realista, identificando vulnerabilidades explotables y analizando su impacto en la confidencialidad, integridad y disponibilidad de la información.

La evaluación siguió principios de metodologías reconocidas como PTES y OWASP, lo que permitió mantener un proceso ordenado desde la fase de reconocimiento hasta la post-explotación. El hallazgo más relevante fue la exposición de credenciales en texto plano dentro de /readme.txt, lo cual facilitó acceso inicial por FTP y posteriormente por SSH, para finalmente escalar privilegios mediante la vulnerabilidad DirtyCow (CVE-2016-5195).

🧪 Entorno Host-Only
🛠️ PTES / OWASP
⚠️ Riesgo alto / crítico

1) Contexto del engagement

Objetivo del ejercicio

Evaluar de forma proactiva la postura de seguridad del servidor principal de archivos, simular un ataque real y documentar cómo distintas debilidades pueden encadenarse hasta comprometer el sistema completo.

Alcance

La prueba se limitó a la máquina objetivo My File Server 1, dentro de un entorno de laboratorio con dos máquinas virtuales: Kali Linux como atacante y el servidor vulnerable como objetivo.

2) Metodología aplicada

El proceso de evaluación se desarrolló siguiendo un flujo estructurado alineado a PTES y a buenas prácticas de OWASP. Primero se realizó reconocimiento de red para localizar el host activo. Posteriormente se ejecutó enumeración de servicios y análisis de recursos expuestos, lo que permitió detectar vectores de acceso como HTTP, FTP, SMB y SSH.

Una vez identificados los servicios, se investigaron debilidades concretas en la configuración del sistema y se verificó la viabilidad de explotación. La prueba avanzó desde exposición de credenciales hasta acceso remoto persistente y escalada de privilegios, demostrando que una cadena de fallos relativamente simples puede terminar en control administrativo del servidor.

Fases ejecutadas

  • Reconocimiento de superficie de ataque.
  • Enumeración de servicios y recursos compartidos.
  • Identificación de credenciales expuestas y configuraciones inseguras.
  • Explotación de acceso inicial.
  • Acceso remoto mediante SSH.
  • Escalada de privilegios con DirtyCow.

3) Desarrollo técnico del ataque

Reconocimiento inicial

En la etapa de descubrimiento se identificó la máquina dentro de una red aislada Host-Only. Posteriormente, el escaneo de puertos y servicios permitió detectar componentes relevantes del sistema, entre ellos servicio web, FTP, SMB y SSH. Esta etapa fue esencial porque definió la superficie de ataque inicial y permitió orientar la enumeración hacia posibles puntos débiles.

Enumeración de recursos

Durante la enumeración se identificó un archivo expuesto: /readme.txt. El contenido de este archivo reveló una contraseña almacenada en texto plano: rootroot1. Este hallazgo fue crítico, ya que evidenció una mala práctica severa de gestión de credenciales y abrió la posibilidad de reutilizar la contraseña sobre otros servicios activos del sistema.

Acceso por FTP

Con las credenciales descubiertas, se intentó autenticación contra el servicio FTP utilizando el usuario identificado durante la enumeración de Samba: smbuser. El acceso fue exitoso, lo que confirmó que las credenciales expuestas eran válidas y reutilizadas en el sistema.

Una vez dentro, se exploró el directorio del usuario autenticado y se encontró que la sesión FTP correspondía a /home/smbuser. A partir de ello, se preparó una técnica para conseguir acceso remoto persistente mediante claves SSH.

Preparación de acceso remoto por SSH

El siguiente paso consistió en generar un par de claves SSH en la máquina atacante y cargar la clave pública al servidor objetivo. Para ello se creó el directorio .ssh y posteriormente se subió la clave pública al archivo authorized_keys. Esta acción permitió preparar autenticación por clave sin necesidad de contraseña, aprovechando el acceso FTP previamente obtenido.

Tras completar este proceso, se probó el acceso al servicio SSH y se estableció una sesión remota exitosa como el usuario smbuser. Con ello, el acceso inicial dejó de depender únicamente del FTP y pasó a ser una sesión interactiva más estable para continuar la evaluación.

Escalada de privilegios con DirtyCow

Ya dentro del sistema, se verificó información básica mediante comandos como whoami, pwd y uname -a. Esto reveló que el servidor ejecutaba un kernel Linux 3.10.0-229.el7.x86_64, una versión vulnerable a CVE-2016-5195 (DirtyCow).

DirtyCow es una vulnerabilidad del kernel Linux asociada a una condición de carrera en el mecanismo Copy-On-Write, la cual permite a un usuario local escalar privilegios hasta root. Se identificó un exploit funcional, se preparó en el sistema comprometido y se utilizó para obtener privilegios elevados, logrando así el control total del servidor.

Interpretación del riesgo

El nivel general del sistema se considera crítico porque un atacante externo, a partir de una cadena corta de errores, puede pasar de reconocimiento a compromiso total del activo. La exposición de credenciales, combinada con servicios inseguros y kernel vulnerable, generó una ruta clara hacia root.

7) Conclusión

Esta actividad demuestra cómo un error aparentemente simple, como dejar una contraseña en texto plano dentro de un archivo accesible, puede convertirse en el punto de partida para comprometer completamente un sistema. El caso de My File Server 1 evidencia la importancia de controlar la exposición de secretos, eliminar servicios inseguros y mantener actualizado el sistema operativo para reducir el riesgo de escalada.

Desde una perspectiva de ciberseguridad defensiva, el ejercicio confirma que la postura de seguridad no depende de una sola barrera, sino del encadenamiento correcto de múltiples controles. Cuando varios fallos coinciden, la probabilidad de compromiso total se vuelve alta.
