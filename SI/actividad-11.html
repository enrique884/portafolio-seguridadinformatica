Red team report: pentesting de Napping 101

Evaluación ofensiva de un entorno web vulnerable, enfocada en Tabnabbing, robo de credenciales, acceso inicial por SSH y escalada de privilegios mediante manipulación de un script ejecutado automáticamente.

Introducción

Esta actividad documenta una evaluación ofensiva realizada sobre la máquina vulnerable Napping 101, con el fin de medir su exposición frente a un escenario realista de ataque. El enfoque principal se centró en debilidades web, particularmente una vulnerabilidad asociada al manejo de enlaces externos que permitió desarrollar un ataque de tipo Tabnabbing.

A partir de esa vulnerabilidad fue posible capturar credenciales válidas de un usuario legítimo, conseguir acceso inicial al sistema y continuar con una fase de post-explotación basada en permisos inseguros sobre un script automatizado. La manipulación de dicho componente permitió ejecutar una reverse shell y escalar privilegios hasta comprometer completamente el servidor.

🌐 Objetivo: Napping 101
🎣 Vector: Tabnabbing
🚨 Riesgo: crítico

1) Executive summary y alcance

Resumen ejecutivo

Durante la evaluación se identificó una vulnerabilidad crítica en el manejo de enlaces externos, la cual permitió la ejecución de un ataque de ingeniería social técnica orientado al robo de credenciales. Con esa información se obtuvo acceso inicial al sistema y posteriormente se aprovechó un script con permisos inseguros para elevar privilegios y lograr compromiso total del servidor.

Scope

Las pruebas se realizaron en un laboratorio controlado, usando Kali Linux como máquina atacante y Napping 101 como máquina objetivo. Se evaluaron principalmente la aplicación web, el servicio SSH y posibles mecanismos de escalada asociados a archivos y scripts locales.

2) Metodología aplicada

La evaluación siguió una metodología alineada con PTES y OWASP. En primer lugar se llevó a cabo el reconocimiento inicial para identificar activos y servicios expuestos. Con herramientas de descubrimiento y escaneo se detectó un servidor web en el puerto 80 y un servicio SSH en el puerto 22, los cuales fueron considerados como vectores relevantes de ataque.

Posteriormente se realizó un análisis específico del comportamiento de la aplicación web con base en lineamientos de OWASP, enfocándose en la gestión de enlaces externos. Esta revisión permitió detectar la ausencia de mecanismos defensivos como noopener y noreferrer, lo cual hacía posible un escenario de Tabnabbing mediante manipulación del objeto window.opener.

Fases ejecutadas

  • Reconocimiento y enumeración.
  • Análisis web enfocado en Tabnabbing.
  • Explotación del vector de robo de credenciales.
  • Acceso inicial al sistema mediante credenciales válidas.
  • Post-explotación, reverse shell y escalada de privilegios.

3) Desarrollo técnico del ataque

Reconocimiento y servicios expuestos

Durante el reconocimiento se identificó la presencia de un servidor web y un servicio SSH. La aplicación web fue priorizada como principal vector de análisis porque representaba la superficie de ataque más accesible y además podía interactuar con usuarios reales mediante formularios y enlaces.

Detección del vector Tabnabbing

El análisis reveló que el campo “Blog Link” aceptaba enlaces externos sin controles adecuados. La ausencia de protección en redireccionamientos permitió desarrollar una técnica de Tabnabbing: se construyó un recurso HTML malicioso capaz de manipular la pestaña original del navegador y presentar una interfaz falsa para capturar credenciales del usuario.

Para ello se habilitó un servidor temporal con python3 -m http.server, alojando el contenido malicioso necesario para simular el ataque y recolectar los datos.

Obtención de credenciales y acceso inicial

Una vez que el usuario interactuó con el enlace malicioso, fue posible capturar credenciales legítimas. Estas credenciales permitieron el acceso inicial al sistema, abriendo la puerta a una fase más avanzada de explotación. A partir de este punto, el pentest dejó de centrarse únicamente en la capa web y comenzó a evaluar la postura interna del sistema comprometido.

Permisos inseguros y reverse shell

Durante la exploración del sistema se detectó un script con permisos inseguros: query.py. Este archivo podía ser modificado por un usuario de bajo nivel, lo que representaba una oportunidad clara para inyectar código malicioso. Además, el script era ejecutado automáticamente, lo que convirtió esta debilidad en un canal ideal para ejecutar una reverse shell y moverse a una cuenta con mayores privilegios.

Escalada de privilegios

La combinación de un acceso inicial válido y un script automatizado sin controles suficientes permitió llevar la intrusión hasta un escenario de compromiso total. Como resultado, se obtuvo control del sistema comprometido, confirmando un riesgo crítico para la organización bajo análisis.

Síntesis del impacto

El riesgo se considera crítico porque el atacante pudo vulnerar defensas web, comprometer cuentas de usuarios y escalar hasta control administrativo total del sistema. Esto implica amenaza directa para la confidencialidad, la integridad y la disponibilidad de la infraestructura.

7) Conclusión

Esta actividad evidencia cómo una vulnerabilidad web aparentemente pequeña puede convertirse en el punto de partida para una intrusión de alto impacto. El caso de Napping 101 demuestra que la falta de protección en enlaces externos, combinada con permisos inseguros y automatización deficiente, puede escalar rápidamente hacia un compromiso total de la infraestructura.

Desde la perspectiva de seguridad informática, el laboratorio refuerza la importancia de aplicar principios de desarrollo seguro, proteger las sesiones web, restringir permisos sobre scripts y auditar tareas automáticas que puedan ser manipuladas.
